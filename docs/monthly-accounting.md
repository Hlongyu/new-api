# 管理员月度记账

入口：统计 → 消费数据 → 月度记账。接口仅管理员可读：

- `GET /api/data/monthly-accounting?year=2026`
- `GET /api/data/monthly-accounting/users?period=2026-10&p=1&page_size=20`

## 业务口径

本站约定卖码即兑换，没有已售未兑中间态；网页余额数字 1 单位按人民币 1 元记账。仅统计兑换码实际入账，不把生成兑换码视为收款。此报表依赖所有充值均来自等价付费兑换码、没有额外赠送或人工现金退款的业务前提；如果以后改变，应扩展资金流水后再继续使用本公式。

2026-10-01 00:00（北京时间，UTC+8）为切换起点：全站用户钱包余额为期初未消费预收款，包含管理员、禁用和软删除账号。不会自动把这些存量余额确认成十月收入。

当月消费收入 = 期初未消费预收款 + 两次快照之间的兑换码收款 − 期末未消费预收款。

2026-11-01 的快照形成首份完整的十月报表。尚无月末快照的月份不显示零收入，而显示未完成。报表不是利润表：上游实际消耗、手续费、服务器费等需另外扣除。十月报表自动计入一次旧账冲回：旧账冲回 = −10 月 1 日期初真实余额；记账收入 = 消费收入 + 旧账冲回，即十月兑换收款 − 十月期末余额。允许十月记账收入为负，且不会因此标记异常。十一月起冲回为 0。真实余额快照与正常消费收入始终保留，不改写历史余额。重复查询不会重复扣减，因为调整按月份计算，不修改账户或写入重复扣费。

## 数据保存

- `accounting_redemptions`：兑换成功时，与额度入账同一事务写入不可变收款记录。兑换码后续修改、清理不会改写此记录。旧兑换记录不回填，首份快照的累计收款数建立比较基准。
- `accounting_snapshots`：每月一份，包含计划时间、实际采集时间、原始总余额、累计收款、人数、换算系数和状态。
- `accounting_snapshot_users`：该快照中的每个用户 ID、用户名、原始余额及删除状态，可分页查看历史明细。

使用数据库一致性事务读取余额及累计收款；SQLite 使用 serializable，MySQL/PostgreSQL 使用 repeatable read。余额明细按主键分批读取，汇总从已保存明细计算。月标识唯一约束避免重启、重试或多个主节点重复采集；失败事务不会留下部分明细或占用该月份。

金额以原始 quota 的 64 位整数保存。首次快照按当时网页余额展示方式换算（`QuotaPerUnit / GetUsdToCurrencyRate(...)`），固定为 `quota_per_cny`，之后历史账目不随展示汇率改变。TOKENS 展示模式不创建财务快照。

## 调度与截止口径

主节点启动后检查当月，并对齐每个整分钟检查，包含每月一号 00:00。实际采集时间保存在快照中；这不是纳秒级的午夜历史回放。

- 一分钟内成功采集：`captured`。
- 错过月初一分钟，或采集耗时越过该窗口：`late`。保留真实采集的余额，不伪造月初余额。
- 启用了进程内批量更新：`batch_pending`。无法保证其他节点内存中的未落库余额一致，需核对。
- 有负钱包余额：`negative_balance`，需核对，不能把欠款抵减预收款后当成已收现金收入。
- 缺少任一端点、异常快照、借款偿还、累计收款倒退或负收入：不生成可直接使用的月度收入数字。

快照反映数据库已记账的钱包余额。跨月的在途请求/任务可能仍有预扣、退款或后续结算，归属按照实际钱包记账时点，而不是请求开始时间。需要严格按服务完成时间进行财务结账时，应核对这些在途项目。

上线要求：在北京时间 2026-10-01 00:00 前完成所有节点升级和数据库迁移，保持至少一个主节点运行，所有节点关闭余额批量延迟更新。不能只升级调度节点：旧版本的兑换节点不会写入新增收款表。数据库备份需要同时覆盖快照、明细和收款表；消费日志清理不影响这些表。

错过的历史月份只显示缺失或待核对，不会从当前余额自动倒推，也没有开放修改历史快照的接口。
